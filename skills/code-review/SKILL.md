对 `HEAD` 与用户指定固定点之间的 diff 进行双维度评审：

- **标准**：代码是否遵循本仓库成文的编码规范？
- **规格**：代码是否忠实实现了最初的 issue / 规格？

两个维度都作为**并行子代理**运行，以免彼此污染上下文，再由本 skill 汇总它们的结论。每个子代理都从全新的上下文窗口开始。

## 流程

### 1. 敲定固定点

用户所说的就是固定点（commit SHA、分支名、tag、`main`、`HEAD~5` 等）。如果用户没有指定，就主动询问。

一次性确定 diff 命令：`git diff <固定点>...HEAD`（三点式，使比较基准为 merge-base）。同时用 `git log <固定点>..HEAD --oneline` 记下提交列表。

继续往下之前，先确认固定点可以解析（`git rev-parse <固定点>`）且 diff 非空。无效的 ref 或空 diff 应该在这里就失败，而不是到两个并行子代理里才失败。

### 2. 确定规格来源

按以下顺序寻找最初的规格：

1. 提交信息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等），通过追踪器文档中描述的流程获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能相符的规格文件。
4. 如果都没有找到，询问用户规格在哪里。若用户表示没有规格，**规格**子代理将跳过，并报告“无可用规格”。

### 3. 确定标准来源

在仓库中搜索所有记录“代码应当如何编写”的文件。存在 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md` 时，它们必须在清单中。

在仓库自身成文规范之上，标准维度始终携带下面这套**坏味道基线**：一组固定的 Fowler 代码坏味道（《重构》第 3 章），即使仓库什么都没写也照样适用。有两条规则约束它：

- **仓库优先。** 仓库成文的规范永远优先；如果它认可了基线会标记的写法，就不再报该坏味道。
- **永远是主观判断。** 每个坏味道都只是带标签的启发式提示（“疑似 Feature Envy”），从不作为硬性违规。与这里其他标准一样，跳过工具链已经强制检查的内容。

每个坏味道按 *它是什么* → *怎么修* 来读，并与 diff 对照匹配：

- **神秘命名（Mysterious Name）**：函数、变量或类型的名字无法揭示它做了什么或存了什么。→ 重命名；如果找不到诚实的名字，说明设计本身含混。
- **重复代码（Duplicated Code）**：相同的逻辑形态在本次改动的多个 hunk 或文件中出现。→ 提取共同形态，两处都调用它。
- **依恋情结（Feature Envy）**：某个方法访问另一个对象的数据比访问自己的还多。→ 把该方法搬到它所依恋的数据上。
- **数据泥团（Data Clumps）**：同样的几个字段或参数总是结伴出现（一个想要诞生的类型）。→ 把它们打包成一个类型，传递这个类型。
- **基本类型偏执（Primitive Obsession）**：用基本类型或字符串代替本应拥有独立类型的领域概念。→ 给这个概念一个自己的小类型。
- **重复的 switch（Repeated Switches）**：针对同一类型的相同 `switch` / `if` 级联在本次改动中反复出现。→ 改用多态，或让两处共享同一张映射表。
- **霰弹式修改（Shotgun Surgery）**：一处逻辑改动迫使在 diff 中许多文件里做零散修改。→ 把一起变化的东西聚到一个模块里。
- **发散式变化（Divergent Change）**：一个文件或模块因若干互不相关的原因被修改。→ 拆分，使每个模块只因一种原因而变。
- **夸夸其谈通用性（Speculative Generality）**：为规格并不需要的场景添加抽象、参数或钩子。→ 删掉；内联回去，直到出现真实需求。
- **过长的消息链（Message Chains）**：调用方不该依赖的长链 `a.b().c().d()` 导航。→ 用第一个对象上的一个方法把这段游走隐藏起来。
- **中间人（Middle Man）**：一个类或函数大部分只是继续转发。→ 去掉它，直接调用真正的目标。
- **被拒绝的遗赠（Refused Bequest）**：子类或实现者忽略或重写了大部分继承来的东西。→ 放弃继承，改用组合。

### 4. 并行启动两个子代理

把两个子代理调用一起发出，都在前台执行，然后汇总它们返回的报告。

**标准子代理的提示词**应包含：

- 完整的 diff 命令与提交列表。
- 你在第 3 步找到的标准来源文件清单，**外加第 3 步的坏味道基线**全文粘贴（子代理没有其他途径获取它）。
- 任务简报：“按文件/hunk 报告（在相关处）：(a) diff 中每一处违反成文规范的地方：引用该规范（文件 + 规则）；(b) 你发现的任何基线坏味道：点名并引述相应 hunk。区分硬性违规与主观判断：违反成文规范可以是硬性的，但基线坏味道永远只是主观判断，且仓库的成文规范优先于基线。跳过工具链已强制检查的内容。400 词以内。”

**规格子代理的提示词**应包含：

- diff 命令与提交列表。
- 规格的路径或已获取的内容。
- 任务简报：“报告：(a) 规格要求了但缺失或只完成一部分的内容；(b) diff 中没被要求的行为（范围蔓延）；(c) 看起来已实现、但实现方式有问题的地方。每条结论都引述对应的规格原文。400 词以内。”

如果没有规格，跳过规格子代理，并在最终报告中注明这一点。

### 5. 汇总

把两份报告分别放在 `## 标准` 与 `## 规格` 标题下，原文呈现或稍作整理。**不要**合并或重新排序结论，因为两个维度是刻意分开的（见 _为什么分两个维度_）。

最后用一行总结：每个维度的结论总数，以及*各维度内部*最严重的问题（如果有）。不要在维度之间挑出一个总冠军：那正是这种分维度设计所要避免的重新排序。

## 为什么分两个维度

一次改动可以通过一个维度而失败于另一个维度：

- 代码遵循了每一条规范，但实现的是错误的东西 → **标准通过，规格失败。**
- 代码完全实现了 issue 的要求，但破坏了项目约定 → **规格通过，标准失败。**

分开报告可以防止一个维度掩盖另一个维度。
